## V1. Ядро — готово

Проверено запуском:
- `dotnet run` с нуля создаёт `easylang.db` и применяет миграцию.
- Весь поток вручную через `curl`: загрузка `sample.srt` → реплики → разбор с контекстом
  → словарь → `/review/next` → ответ → пересчёт интервала; ошибки 400/404/409.
- Без доступа к словарю `/lines/{id}/explain` отвечает 503 ProblemDetails и ничего не сохраняет.
- `dotnet test tests/EasyLangApi.Tests` — все тесты зелёные.

Написано, но не проверено вживую:
- `DictionaryExplainer` против настоящего api.dictionaryapi.dev (хост закрыт в среде).
- `LlmExplainer` против настоящей модели (нет ключа; тесты на подставном HTTP — в V3).

## V2. Распознавание текста — готово

Проверено запуском:
- Тесты распознают изображения, которые рисуются в самом тесте (ImageSharp + шрифт DejaVu
  из `tests/EasyLangApi.Tests/Assets`): одна строка, два абзаца, битый PNG, нет языка.
- `POST /recognize` вручную на `sample.png`: текст распознан, абзацы сохранены как реплики.
- С `Ocr__TesseractPath=/nonexistent/tesseract` приложение стартует, `/recognize` отвечает 503
  «Tesseract не найден ... Ocr:TesseractPath», остальные эндпоинты работают.
- Распознанные реплики разбираются через тот же `/lines/{id}/explain` (тест).

Если в среде нет tesseract, тесты настоящего распознавания пропускаются (`Assert.Skip`),
а тесты на подставном распознавателе выполняются.

Решения:
- **Tesseract через командную строку**, а не через NuGet-обёртку: обёртки привязаны к версиям
  нативных библиотек и плохо работают на Linux; CLI ставится одинаково везде.
- **Абзац = реплика.** Tesseract разделяет абзацы пустой строкой; строки внутри абзаца склеиваются.
- **`episodeId` в `/recognize`** дописывает скриншот в существующий эпизод, чтобы следующие
  окна диалога видели предыдущие как контекст. Без `episodeId` создаётся новый эпизод.
- Формат файла проверяется по сигнатуре до запуска Tesseract (400 для не-картинок).
- ImageSharp (лицензия Six Labors Split) подключён **только к тестам**.

## V3. Языковая модель — готово

Проверено запуском:
- Тесты без настоящего ключа: сборщик промпта (полный, частичный и пустой контекст),
  разбор ответа (чистый JSON, JSON в markdown, не-JSON, битый JSON), `LlmExplainer`
  на подставном `HttpMessageHandler` (адрес, заголовок Authorization, модель, контекст в промпте,
  `response_format`, коды 401/404/429/502, пустой ответ, обрыв соединения).
- Сквозной тест: с `Llm:ApiKey` и `Llm:BaseUrl` Ollama-вида `/lines/{id}/explain` идёт в LLM.
- Вручную: `dotnet run` с `Llm__BaseUrl` на локальную заглушку OpenAI-совместимого API —
  запрос дошёл, ответ разобран и сохранён. Без настройки работает `DictionaryExplainer`.

Не проверено: настоящие OpenAI / Ollama (нет ключа, нет модели в среде).

Решения:
- **Включатель — непустой `Llm:ApiKey`**, как в SPEC.md. Для Ollama ключ любой (`ollama`).
- **Тело запроса буферизуется** (`StringContent`), а не `JsonContent`: последний шлёт чанки
  без `Content-Length`, и простой совместимый сервер на этом сломался при ручной проверке.
- **Ответ модели не в JSON не теряется**: текст целиком уходит в `summary`.
- Падения LLM не подменяются словарём автоматически: 503 с подсказкой, что проверить в настройках.

## V4. Планировщик повторений — готово

Проверено запуском (тесты):
- `FixedIntervalScheduler`: лесенка, настраиваемые ступеньки.
- `AdaptiveScheduler`: интервалы растут с верными ответами, ошибка укорачивает интервал,
  фраза, которую вспоминали после долгих перерывов, получает `Ease > 1` и более длинный интервал,
  быстро забываемая — `Ease < 1`; в момент `DueAt` вероятность забыть равна `1 − TargetRetention`;
  показы без ответа не влияют на расчёт.
- Выбор планировщика через `Review:Scheduler`; неизвестное значение останавливает запуск.
- Отбор реплик «ровно один незнакомый элемент»: `SingleUnknownSelector`, `/review/next`,
  `/vocabulary/{id}/examples`.
- Папка `srs/` не создавалась и не используется; `EasyLangApi.csproj` исключает её из сборки.

Решения:
- **Модель адаптивного планировщика** — полураспад памяти (по мотивам half-life regression,
  Settles & Meeder 2016) с общими весами из конфигурации и **поправкой сложности на элемент**,
  которая подбирается по его `ReviewEvent` перебором по сетке [−3; 3] с нормальным априорным.
  Веса общей модели не обучаются по данным пользователя — это следующий шаг для ВКР.
- В `Ease` адаптивный планировщик пишет множитель периода полураспада `2^d`; фиксированный `Ease` не трогает.
- **«Незнакомое»** = элемент словаря с `IntervalDays < Review:KnownAfterDays` (21). Слова, которые
  пользователь не смотрел, считаются знакомыми: другого источника знаний о словаре пока нет.
- Кандидаты ищутся SQL `LIKE` по самому длинному слову фразы (до 200 реплик), точная проверка — по словам.
- `/review/next` по-прежнему выбирает самый просроченный элемент; меняется только реплика для показа.

## V5. Пользователи и квоты — готово

Проверено запуском (тесты):
- Регистрация, вход, `/auth/me`; пароль хранится только хешем; одинаковый ответ на
  неверный пароль и неизвестный email; подделанный токен — 401.
- Access-токен истекает через 15 минут (сдвиг подставных часов), refresh выдаёт новую пару;
  повторное использование старого refresh-токена отзывает и новый; refresh истекает через 30 дней;
  logout отзывает токен. Короткий `Jwt:SigningKey` останавливает запуск.
- **Чужие данные недоступны**: у второго пользователя пустые списки, а прямые id чужих
  эпизодов, реплик, элементов, показов и дописывание в чужой эпизод — 404. Одна фраза у двух
  пользователей — два разных элемента. Отбор «i + 1» не видит чужой словарь.
- Лимит в минуту на `/lines/{id}/explain` и `/recognize` — 429 ProblemDetails, у каждого пользователя
  своё окно, дешёвые эндпоинты не ограничены. Суточная квота разборов сбрасывается на следующий день.

Проверено вручную:
- База, созданная версией V4 с данными, мигрирует: данные переходят пользователю `legacy@localhost`,
  войти под ним нельзя, новый пользователь их не видит (404).
- `dotnet run` → регистрация → загрузка → `/episodes` с токеном; без токена 401.

Решения:
- **Глобальные фильтры EF Core** по владельцу вместо `Where(UserId == ...)` в каждом запросе:
  нельзя забыть фильтр. В тестах прямой доступ к базе — через `IgnoreQueryFilters()`.
  Владелец хранится в `Episode.UserId` и `KnowledgeItem.UserId`; `Line`, `Lookup`, `ReviewEvent`
  фильтруются через навигацию.
- Чужое — **404, а не 403**: не раскрываем, что такой id существует.
- Все эндпоинты закрыты политикой по умолчанию (`FallbackPolicy`), открыты только `/auth/*`
  и старый `/translate`.
- Время жизни JWT проверяется через тот же `TimeProvider`, что выдаёт токен (свой `LifetimeValidator`),
  поэтому истечение проверяется тестами без ожидания.
- **Без `Jwt:SigningKey` ключ генерируется при запуске** с предупреждением в логе — `dotnet run`
  с чистого клона работает без настройки. В Docker ключ задаётся переменной окружения.
- Лимиты в минуту — встроенный `RateLimiter` в памяти (сбрасывается при перезапуске);
  суточная квота считается по `Lookup` в базе.
- Данные V1–V4 при миграции не удаляются, а передаются служебному пользователю.

Не сделано: подтверждение email, сброс пароля, удаление пользователя.

## V6. Docker и CI — готово

Проверено запуском:
- `Dockerfile` (многоэтапный: SDK → aspnet + Tesseract, пользователь `app`, база в томе `/data`)
  собран и запущен: `/health`, регистрация, загрузка `sample.srt`, распознавание `sample.png`
  Tesseract'ом внутри контейнера.
  **Оговорка:** в этой среде контейнер сборки не доверяет TLS-прокси песочницы, поэтому собиралась
  копия Dockerfile, в которую добавлены только две строки с сертификатом прокси после каждого `FROM`.
  Сам `Dockerfile` из репозитория в чистом виде здесь не собирается — из-за среды, а не из-за него.
- `docker compose config` валиден; `docker compose up --no-build` с этим образом поднимает API,
  `JWT_SIGNING_KEY` из окружения подхватывается.
- Workflow проверен `actionlint`; его шаги (Release-сборка, тесты с trx-логгером, скрипт проверки
  контейнера) выполнены локально и прошли.

Не проверено:
- Сам запуск в GitHub Actions (ветка не запушена — см. «Ветка и публикация»).
- Профиль `llm` с Ollama: образ `ollama/ollama:0.12.6` существует, но не запускался, модель не скачивалась.

Решения:
- `/health` (без токена) — для проверки контейнера.
- Ollama — в профиле `llm`, чтобы по умолчанию не тянуть гигабайты.
- Секреты — через `.env` (в `.gitignore`), пример — `.env.example`.
- EF при миграции `AddUsers` пишет предупреждение 20410 («PRAGMA foreign_keys нельзя выполнить
  в транзакции») — это штатная перестройка таблиц SQLite, на результат не влияет.

## V7. Десктопный клиент — написан, **не проверен на Windows**

- `client/EasyLangClient` — WinForms, `net10.0-windows`: иконка в трее, глобальный хоткей
  (`RegisterHotKey`), стоп-кадр всех мониторов и выбор области мышью, отправка PNG на `/recognize`
  с заголовком активного окна как `title` и `episodeId` для продолжения диалога, окно с кликабельными
  словами и разбором через `/lines/{id}/explain`, вход/регистрация, обновление токена при 401.
- Вся логика на сервере, клиент — только захват экрана и показ ответов.

Проверено: **только компиляция** на Linux (`EnableWindowsTargeting`, 0 предупреждений).
Не запускался ни разу: облачная среда не может запустить Windows-приложение.
Не проверены хоткей, захват экрана, DPI, работа поверх полноэкранных игр.

Независимость: корневой `EasyLangApi.csproj` исключает `client/**`, тесты клиент не используют;
в CI клиент собирается отдельным заданием на `windows-latest` с `continue-on-error: true`.

Решения:
- WinForms, без дизайнера (интерфейс в коде) — меньше файлов, проще генерировать и читать.
- Стоп-кадр снимается до показа рамки выбора: игра может продолжать анимацию, рамка не попадает в снимок.
- Токены — только в памяти клиента, после перезапуска нужен вход.

## Решения V1, принятые без владельца

- **Проект остался в корне** (`dotnet run` из корня клона), тесты — `tests/EasyLangApi.Tests`.
  В `EasyLangApi.csproj` из сборки исключены `tests/`, `client/`, `srs/`, `docs/`, чтобы
  чужие `.cs` не попадали в приложение. `.sln` нет: с ним и `.csproj` в одной папке
  `dotnet build` без аргументов перестал бы работать.
- **`Lookup.KnowledgeItemId`** — добавлен к схеме из SPEC.md: наблюдение явно ссылается на элемент учёта.
- **`PhraseContext.CurrentLine`** — добавлено к полям `Title/Speaker/Before/After`: сама реплика с фразой.
  `Speaker` берётся из префикса реплики вида `MAYA: ...`.
- **`IPhraseExplainer.ExplainAsync`** получил необязательный `CancellationToken`.
- **Нормализация**: нижний регистр, единый апостроф, без пунктуации, слова через пробел.
  `"Spill the BEANS?"` и `"spill the beans"` — один `KnowledgeItem`.
- **Новый элемент доступен для повторения сразу** (`DueAt = now`), чтобы поток проходился за одну сессию.
- **`GET /review/next` создаёт `ReviewEvent`** с `ShownAt`, а `POST /review/{id}` принимает
  `reviewId` этого показа и дописывает `AnsweredAt`/`WasCorrect`. Так в истории остаются
  и показы без ответа. Повторный ответ на тот же показ — 409.
- **Интервал в V1** — лесенка 1, 3, 7, 14, 30, 60, 120 дней, дальше удвоение; ошибка — снова 1 день.
  `Ease` хранится (2.5), но в V1 не используется.
- **Словарь и выражения**: если выражение целиком не найдено, показываются значения отдельных слов,
  но `found = false` и `summary = null` — это не смысл фразы.
- **Ошибки внешних сервисов** — `ExplainerUnavailableException` → 503 через `IExceptionHandler`.
- `launchBrowser` выключен: веб-интерфейса нет. Эндпоинт `/translate` из исходного шаблона оставлен.

## Известные ограничения и что дальше

- Одновременный первый разбор одной и той же новой фразы одним пользователем может упасть
  на уникальном индексе (500). Не исправлялось.
- Веса общей модели адаптивного планировщика заданы в конфигурации, а не обучены на `ReviewEvent`
  всех пользователей — естественный следующий шаг для ВКР.
- Нет подтверждения email, сброса пароля, удаления пользователя.
- Лимиты в минуту хранятся в памяти процесса: при нескольких экземплярах сервера каждый считает свои.
- `/review/next` создаёт `ReviewEvent` на каждый вызов (так задумано: показ — это событие),
  поэтому повторные вызовы без ответа видны в истории как отдельные показы.

# eval — словарь, LLM без контекста и LLM с контекстом

Проверяем главную гипотезу проекта: разбор фразы с контекстом сцены объясняет сленг
и многозначные слова лучше, чем словарь и чем та же модель без контекста.

> **Настоящих прогонов пока не было.** Результатов на настоящих моделях в репозитории нет.
> Скрипт проверен только на подставном сервере, его числа подстроены и ничего не говорят о моделях
> (см. «Что проверено»).

Отдельный проект на Python 3.10+, только стандартная библиотека, проверялся на 3.13.
От основного приложения он не зависит. C# не подошёл: корневой `EasyLangApi.csproj`
собирает все `*.cs` из подпапок, кроме `tests/`, `client/`, `srs/` и `docs/`.

## Что сравнивается

| Вариант | Что делает | Откуда логика |
|---|---|---|
| `dictionary` | dictionaryapi.dev. Если выражение не найдено целиком (404, а для выражения из нескольких слов и 5xx), ищет отдельные слова; значения сортируются по общим словам с контекстом. Оценивается первое значение | `Explaining/DictionaryExplainer.cs` (сверено с prototype 3f81371) |
| `llm_plain` | LLM с промптом приложения, но без контекста: только фраза и «No context is available» | `Explaining/PromptBuilder.cs` с `PhraseContext.Empty` |
| `llm_context` | LLM с контекстом, как в приложении: название, говорящий, две реплики до, сама реплика, две после | `Explaining/PromptBuilder.cs`, `Lookups/LookupService.cs` |

Промпт и разбор ответа модели скопированы в `easylang_eval/prompts.py`. Если промпт в приложении
меняется, копию нужно обновить. Тест `test_matches_csharp_source` сверяет системный промпт
с `PromptBuilder.cs` и упадёт, если они разойдутся.

## Набор фраз

`data/phrases.jsonl`, 150 строк:

| Категория | Сколько | Что проверяет |
|---|---:|---|
| `slang` | 70 | сленг и игровой жаргон: *salty, no cap, ghosted, nerfed, kite, cheese…* |
| `polysemy` | 55 | многозначные слова, где контекст выбирает не самое частое значение: *bank* — берег, *pitch* — презентация, *rare* — с кровью… |
| `control` | 25 | те же слова, что в сленге, но верен буквальный смысл: суп *salty*, *spilled the tea* на стол. Ловят модель, которая видит сленг везде |

Все реплики сочинены для этого набора. Произведения выдуманные (*Last Lap Legends*, *Ashfall Station*,
*Paper Crowns* и ещё семь), чужие субтитры не использовались.

Формат строки:

```json
{"id": "s001", "category": "slang", "phrase": "salty",
 "title": "Last Lap Legends", "speaker": "Rico",
 "before": ["…", "…"], "line": "He's still salty about losing to a rookie.", "after": ["…", "…"],
 "correct": "обиженный, раздражённый (из-за проигрыша)",
 "distractors": ["солёный на вкус", "опытный, бывалый"]}
```

- `correct` — правильный смысл в этой сцене, по-русски, на этом языке объясняет приложение.
- `distractors` — 1–3 правдоподобных неверных смысла: обычно буквальный или другой смысл того же слова.

При загрузке проверяется:
- фраза стоит в реплике целыми словами, по тем же правилам, что `PhraseNormalizer`;
- по две реплики до и после;
- id не повторяются;
- правильный смысл не совпадает с неверными.

## Как оценивается ответ

Сравнивать свободный текст объяснения с эталоном по словам ненадёжно. Поэтому ответ оценивает
**LLM-судья, который выбирает смысл из списка.** Судья получает:
- текст объяснения: перевод и смысл, а у словаря первое значение;
- пронумерованные варианты: правильный смысл, неверные смыслы и «ни один не подходит».

Устройство судьи:
- Порядок вариантов перемешан и зависит только от id фразы, поэтому одинаков для всех трёх вариантов.
- Ни фразу, ни реплику, ни контекст судья не видит: в объяснении фраза и её слова заменяются на `[…]`.
  Так сделано после пробы 04.11.2026: судья `llama3.1:8b`, который видел фразу, выбирал правильный смысл
  по своему знанию, даже когда объяснение было о другом. Словарь объяснил `no cap` как шапку,
  а судья поставил «без вранья». Версия судьи записывается в `run.json`, старые вердикты при продолжении не используются.
- Какой вариант дал объяснение, он тоже не знает.
- Температура 0. Пустое объяснение судье не отправляется и сразу считается «ни один».

Ответ попадает в одну из категорий:
- **correct** — объяснение совпало с правильным смыслом;
- **distractor** — с неверным;
- **none** — ни с каким;
- **unparsed** — ответ судьи не разобрался.

Сбой сервиса считается ошибкой, а не неверным ответом, и в точность не входит.

## Как запустить с настоящей моделью

Нужен любой API, совместимый с OpenAI Chat Completions (`POST {base}/chat/completions`).

Ключ лучше передавать через переменную окружения, а не аргументом, чтобы он не попал
в историю командной строки. В `run.json` и в отчёт ключ не пишется.

### Внешний API

```bash
cd eval
export EVAL_BASE_URL=https://api.openai.com/v1
export EVAL_API_KEY=...          # ваш ключ
export EVAL_MODEL=gpt-4o-mini
```

Сначала пробный запуск на пяти фразах:

```bash
python3 -m easylang_eval run --limit 5
```

Откройте `out/gpt-4o-mini/results.csv` и убедитесь, что ответы осмысленные. Затем полный прогон
в ту же папку: пять готовых фраз повторно не запрашиваются.

```bash
python3 -m easylang_eval run --workers 4
```

Подойдёт любой другой совместимый сервис: поменяйте `EVAL_BASE_URL` и `EVAL_MODEL`.

### Ollama

```bash
ollama pull qwen2.5:7b
```

```bash
cd eval
python3 -m easylang_eval run --base-url http://localhost:11434/v1 --model qwen2.5:7b
```

Ollama ключ не проверяет. Без `--api-key` заголовок `Authorization` не отправляется.
Если версия Ollama или другой сервер отвечает 400 на `response_format`, скрипт подскажет
добавить `--no-json-mode`.

### Отдельный судья (рекомендуется)

По умолчанию судья — та же модель, и отчёт об этом предупреждает: модель может быть
снисходительна к своим ответам. Лучше взять другую, желательно более сильную модель:

```bash
export EVAL_JUDGE_BASE_URL=https://api.openai.com/v1
export EVAL_JUDGE_API_KEY=...
export EVAL_JUDGE_MODEL=gpt-4o
python3 -m easylang_eval run --base-url http://localhost:11434/v1 --model qwen2.5:7b
```

### Сколько это запросов

Полный прогон делает:
- 300 запросов к модели разбора: 150 фраз × 2 варианта;
- до 450 запросов к судье;
- 150–600 запросов к словарю: выражения из нескольких слов добиваются поиском по отдельным словам.

Цену и время на настоящей модели я не измерял.

### Полезные опции

| Опция | Зачем |
|---|---|
| `--limit N`, `--ids s001,p004`, `--category slang` | прогнать часть набора |
| `--variants llm_context,dictionary` | только некоторые варианты |
| `--out DIR` | папка прогона, по умолчанию `out/<модель>` |
| `--fresh` | начать заново в той же папке |
| `--workers N` | параллельные запросы, для Ollama оставьте 1 |
| `--retries`, `--timeout` | повторы при 429/5xx и обрыве (пауза 2, 4, 8 с), таймаут запроса |
| `--seed N` | передать seed в API, если сервис его поддерживает |
| `--dictionary-url` | другой адрес словаря |

Прогон можно прервать в любой момент. Повторный запуск с той же папкой запросит только то, чего
нет или что закончилось ошибкой. Если в папке прогон с другой моделью или другим набором,
скрипт откажется продолжать и попросит `--fresh` или новую `--out`.

Пересчитать отчёт по готовым файлам без запросов:

```bash
python3 -m easylang_eval report --out out/qwen2.5_7b
```

### Что получится

В папке прогона:
- `results.md` — точность каждого варианта с 95 % интервалом Уилсона, разбивка по категориям,
  сколько раз в контрольных фразах выбран сленговый смысл, парное сравнение с точным тестом Макнемара, ошибки;
- `results.csv` — каждый ответ рядом с выбором судьи и правильным смыслом. В колонке `manual_ok` удобно
  вручную проверить случайные 30–50 строк: так видно, можно ли доверять судье;
- `answers.jsonl`, `judgments.jsonl` — сырые ответы сервисов и судьи;
- `run.json` — настройки прогона без ключей.

Папка `out/` в `.gitignore`. Если решите сохранить результат в репозиторий, копируйте
`results.md` вместе с `run.json`, чтобы было видно, какая модель его дала.

## Слепая проверка судьи

Судья — тоже модель, поэтому его вердикты стоит сверить с человеком. Скрипт готовит для этого выборку:

```bash
python3 -m easylang_eval blind export --run out/qwen2.5_7b --out out/blind
```

Получится:
- `out/blind/blind.csv` — 60 случайных ответов (seed 2026) вперемешку из всех трёх вариантов. В каждой строке
  фраза, объяснение и те же пронумерованные смыслы, что видел судья. Ни варианта, ни вердикта в файле нет.
- `blind_key.json` — ключ, его проверяющий не открывает.
- `INSTRUCTIONS.md` — что делать проверяющему.

Проверяющий вписывает номер смысла в колонку `human_choice`. Потом:

```bash
python3 -m easylang_eval blind score --dir out/blind
```

Скрипт выдаст долю совпадений номера смысла, долю совпадений «верно / неверно» и каппу Коэна,
а также разбивку по вариантам. Результат пишется в `out/blind/agreement.md`.

## Прогон в GitHub Actions

В облачной среде сеть закрыта, поэтому настоящий прогон идёт на раннере GitHub. Workflow
`.github/workflows/eval-live.yml` запускается только пушем в ветку `run/eval`:

1. **Проба.** Ставится Ollama, скачиваются `qwen2.5:7b` (разбор) и `llama3.1:8b` (судья). Прогоняются 6 фраз, по две из каждой категории.
   По измеренному времени `ci/estimate.py` решает, на сколько параллельных задач делить полный прогон,
   чтобы каждая уложилась примерно в 4 часа (`timing.md`).
2. **Части.** Каждая задача берёт фразы `--shard i/N`. Перед стартом она забирает свои сохранённые
   результаты из ветки `results`, поэтому перезапуск продолжает с места обрыва.
3. **Сводный отчёт.** Части собираются командой `merge`.

Результаты кладутся в ветку `results`, в папку `results/eval/` (`probe-judge-v2/`, `shards-judge-v2/`, `full-judge-v2/`; `probe/` — первая проба со старым судьёй), и дублируются в artifact.
Модели никуда не сохраняются.

## Что проверено

Всё ниже запускалось в этой сессии. Настоящая модель и настоящий словарь не вызывались:
ключа нет, а `api.dictionaryapi.dev` закрыт в облачной среде.

Подставной сервер `easylang_eval/mock_server.py` отвечает и как OpenAI-совместимый API, и как словарь.
Ответы он строит по жёстким правилам из набора:
- с контекстом — всегда правильный смысл;
- без контекста — «самое частое» значение фразы;
- словарь знает только отдельные слова;
- судья выбирает вариант, текст которого есть в объяснении.

Значит, итог на заглушке предсказуем по построению: 100 % у `llm_context` — следствие правил,
а не измерение.

Проверено:
- **Тесты.** `python3 -m unittest discover -s tests -t .` — 52 теста, все проходят. Они покрывают:
  - набор фраз;
  - промпт: сверка с C# и случаи из `PromptBuilderTests.cs`;
  - разбор «грязного» JSON;
  - логику словаря;
  - варианты судьи и метрики;
  - повторы HTTP;
  - полный прогон на заглушке: ожидаемые числа, содержимое запросов, неверный ключ,
    отказ от `response_format`, продолжение после обрыва, смену настроек, недоступный сервер,
    Ollama-адрес без ключа.
- **Ручной прогон через командную строку** против заглушки в отдельном процессе:
  - с ключом и с `--workers 4`;
  - каждый 25-й запрос к модели получал 503;
  - сначала `--limit 60`, потом полный запуск в ту же папку.

  Второй запуск взял 180 готовых ответов и запросил остальные 270, все 503 ушли в повторы,
  ошибок 0, отчёт и CSV сформированы.

Повторить проверку самому:

```bash
cd eval
python3 -m easylang_eval.mock_server --port 8089 --fail-every 25
```

В другом терминале:

```bash
cd eval
python3 -m easylang_eval run --base-url http://127.0.0.1:8089/v1 --model mock \
  --dictionary-url http://127.0.0.1:8089/api/v2/entries/en/ --out out/mock
```

## Ограничения

1. **Эталон написан одним автором без проверки носителями.** Реплики и правильные смыслы сочинены
   для набора. Перед выводами стоит дать набор посмотреть второму человеку, лучше носителю.
2. **Контекст искусственный.** Реплики написаны так, чтобы контекст однозначно выбирал смысл.
   В настоящих субтитрах контекст беднее, поэтому преимущество `llm_context` на них, скорее всего, меньше.
3. **Судья — тоже модель.** Возможны ошибки и снисходительность, особенно если судья совпадает с моделью
   разбора. Это лечится отдельным судьёй и ручной проверкой части `results.csv`.
4. **У словаря оценивается одно, первое значение.** Приложение показывает до шести. Если правильное
   окажется вторым, словарь получит «неверно», хотя пользователь мог бы его найти.
5. **Ответы модели недетерминированы.** Температура 0.2, как в приложении. Для выводов в ВКР стоит
   повторить прогон 2–3 раза в разные папки и сравнить.
6. **Выборки маленькие.** 25 контрольных фраз дают интервал шириной около ±15 п.п. Для категорий
   смотрите на интервалы, а не на точечные значения.
